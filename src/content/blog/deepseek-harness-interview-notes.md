# DeepSeek Harness 新手学习笔记:面试也能讲清楚的 12 个核心概念

> 这是配套上一篇《源码解析》的学习资料。上一篇偏"源码怎么写的",这一篇偏"**怎么跟面试官讲明白**"。
> 每个概念都用同一套结构:**一句话** → **生活类比** → **展开** → **30 秒面试回答**。
> 学完这篇,你至少能把 DeepSeek Harness 的核心讲成一个完整、有逻辑的故事。

## 0. 先建立全局印象

### 0.1 一句话:它是什么

**DeepSeek Harness(简称 dsh)是一个开源的"智能体运行框架"——它把"让 AI 模型干活"这件事,做成了一套可以自由拼装、替换、扩展的系统。**

它不是某个具体的 AI 应用(比如聊天机器人),而是"造 AI 应用的地基":模型接入、工具调用、文件读写、安全沙箱、后台任务、网页界面……这些原本要自己从头造的零件,它全部帮你搭好了,而且每个零件都可以换。

### 0.2 一个类比:Agent 的"操作系统"

把电脑类比一下:

- **应用软件** = 一个具体的 agent(比如"帮我写代码的 AI")
- **操作系统** = DeepSeek Harness
- **驱动/外设** = 插件(模型适配器、工具、沙箱……)

操作系统不替你写文档,但它提供"文件系统、进程管理、窗口界面"这些基础能力,让你不用每写一个软件就从零造轮子。Harness 同理:**模型本身(比如 DeepSeek 大模型)是 CPU,harness 是主板和操作系统**。

### 0.3 你需要记住的主线(全文就讲这一件事)

> **dsh 的核心理念只有一句:Everything is a Plugin(一切皆插件)——连"agent 怎么思考"这个核心循环本身都是插件。**

后面所有概念,都是在解释这句话"为什么这样设计、具体怎么实现"。

## 1. 面试题:什么是 agent harness?

- **一句话**:agent 是"会干活的大脑",harness 是"给大脑配齐的手脚、工具和安全带"。
- **类比**:你有菜谱(提示词)和厨师(模型),但要做出一桌菜,还需要厨房、锅碗瓢盆、食材、燃气安全阀——**harness 就是那个厨房**。没有厨房,厨师再厉害也只能"纸上谈兵";没有厨师,厨房再齐全也做不出菜。
- **展开**:实际开发中,一个 agent 要干活,至少需要:能调用工具(执行命令、读写文件、上网搜索)、能记住对话历史、能安全地执行(不能乱删文件)、能和人交互。这些"基建"就是 harness 负责的。dsh 把这些基建全部插件化。
- **30 秒面试回答**:"Agent harness 是智能体的运行框架,负责模型之外的整套基建——工具调用、会话管理、沙箱安全、UI。DeepSeek Harness 的特点是这套基建全部可插拔,连核心循环都是插件,所以叫'一切皆插件'。"

## 2. 面试题:"一切皆插件"到底什么意思?

- **一句话**:系统里**没有"不能改的内核"**,任何一部分(包括 AI 思考的主循环)都可以被替换或叠加。
- **类比**:乐高。没有哪块积木是"焊死"的,你要换轮子就换轮子,要加翅膀就加翅膀。**传统框架像整块塑料模型,想改得用刀削;插件化框架像乐高,想改直接拆装。**
- **展开**:
  - 在 dsh 里,模型适配器、工具注册表、会话日志、agent 循环**都是插件**。
  - 每个插件启动时向共享上下文注册能力,卸载时**自动撤销**(可逆副作用)——不会留下"删不干净"的残留。
  - 好处:想加一个工具,不用改框架代码,写个插件挂上去就行;想换一个思考循环,替换掉默认的那个插件即可。
- **30 秒回答**:"所谓一切皆插件,是指系统没有特权内核。所有能力——包括模型适配、工具、会话日志、甚至 agent 循环本身——都是可注册、可替换、可撤销的插件。想扩展系统只需要'挂一个新插件在旁边',不用 fork 源码改内核。"

## 3. 面试题:Cordis 是什么?为什么用它?

- **一句话**:Cordis 是 dsh 底层的**插件框架**,它规定了"插件之间怎么通信、怎么协作"。
- **类比**:USB 标准。不同厂商的充电器能插进同一个口,是因为大家都遵守 USB 协议。Cordis 就是 dsh 的"USB 标准"——插件们靠它对接。
- **展开**:Cordis 给插件提供三样东西:
  1. **服务**:插件向公共上下文(ctx)注册功能,别的插件可以调用;
  2. **类型化事件**:插件之间通过事件通信(比如"工具要执行了""模型开始回复了"),事件是**类型化的**——写错字段编译期就报错;
  3. **可逆副作用**:插件挂载时注册的一切,卸载时自动清理。
- **30 秒回答**:"Cordis 是驱动 dsh 的插件框架,提供服务注册、类型化事件和可逆副作用三个机制。它让'一切皆插件'成为可能——插件之间通过共享上下文协作,事件驱动整个系统运行。"

## 4. 面试题:Profile、组合包(Bundle)、patch 是什么?

- **一句话**:这三者是"**如何把一堆插件组装成一个可用的 dsh**"的三个概念:Profile 是整台机器,组合包是零件包,patch 是螺丝刀调整。
- **类比**:装一台定制电脑——**Profile 是配置单**(要哪些零件),**组合包是预装好的零件包**(主板+CPU 套装),**patch 是"微调"**(比如把内存超个频)。
- **展开**:
  - **Profile**:一个具名的组装配置,放在 Harness home 目录下,记录"我叠了哪些组合包 + 我自己的微调"。`web` 和 `headless` 是自带的两个模板。
  - **组合包(Bundle)**:一组配置+代码的分发单元。dsh 自带三个:`dsh-base`(最底层:模型/工具/持久化/沙箱/设置/凭据/遥测)、`dsh-web-app`(加浏览器界面)、`dsh-headless`(加一次性运行器,无服务器)。
  - **patch**:一层层"盖上去"的修改。叠加顺序:组合包 → profile 的 patch → home 级的 patch → 命令行 `--patch`。**后盖的层可以覆盖先盖的层**。
  - 查看实际组合结果:`dsh --profile web --dump-config`,打印出的任何条目都能被你的 patch 覆盖。
- **30 秒回答**:"Profile 是插件组装方案,组合包是可分发的一组插件配置,patch 是逐层叠加的修改。系统按固定顺序叠加这些层,后层覆盖前层,所以用户不 fork 源码也能定制一切——因为最后盖上去的是你自己的 patch。"

## 5. 面试题:agent 是怎么"思考"和循环的?

- **一句话**:agent 干活是一个循环:**认领输入 → 让模型想一步 → 调用工具 → 看结果 → 再想下一步**,直到任务完成。
- **类比**:你做一顿饭 = **一个轮次(turn)**;其中"看菜谱 → 下锅炒 → 尝一口"= **一个步骤(step)**。一顿饭可能有很多个步骤。
- **展开**(官方时序图简化版):

```text
轮次开始
  → 认领一条输入(比如用户消息)
  → 组装提示词 + 工具清单(模型能看到的)
  → 送模型:agent/request → 流式回复 assistant/chunk
  → 模型说要调工具 → tool/call
  → 工具执行:前置检查(pre-execute)→ 执行(execute)→ 后置处理(post-execute)
  → 把结果还给模型
  → 模型还要继续?→ 进入下一步;不需要了 → 轮次结束
```

- 关键点:
  - **step = 一次模型请求 + 它调用的工具;turn = 一组连续 step**,直到"不再欠下任何工作"。
  - 每一步之间,历史是从**会话日志**重新派生的(不是模型自己记着)。
  - 整个循环被**事件**驱动,插件可以在各个阶段"插一脚"(比如在工具执行前做审批)。
- **30 秒回答**:"agent 循环分两层:step 是'模型请求+工具调用',turn 是多个 step 组成的完整回合。流程是认领输入、组装提示词、请求模型、执行工具、回传结果,循环到不再有工作为止。这个循环本身是插件,可以被替换,所有环节都有事件可以拦截。"

## 6. 面试题:会话日志为什么这么重要?

- **一句话**:dsh 把整个对话过程记成一本"**只追加、不可篡改的流水账**",模型看到的一切都来自这本账,而且**"模型能看到的一定被记下来了"**。
- **类比**:行车记录仪。出了事故(或要复盘),回放录像就能还原全部经过——不需要司机(模型)自己"凭记忆复述",因为录像(日志)才是唯一真源。
- **展开**:
  - 会话日志是**仅追加**的事件流(`SessionEvent`),是模型上下文的唯一来源。
  - **派生能力**:fork(从某处克隆出新会话)、resume(恢复旧会话)、transcript(导出文本)、UI 回放、遥测——全部从这同一本日志派生。
  - **硬性不变式**:"模型可见即已记录"——凡是发给模型的内容,必须能从日志重建;做不到就要新增一种日志事件。这从架构上杜绝了"模型看到了但系统不知道"的状态漂移。
- **30 秒回答**:"会话日志是 dsh 的唯一真源,一条只追加的事件流。模型历史从日志派生,而不是模型自带记忆;fork、恢复、回放、导出都靠它。最关键是'模型可见即已记录'的不变式,保证了可审计、可复现。"

## 7. 面试题:工具系统是怎么设计的?

- **一句话**:工具 = 给模型开的"**API 接口**",但接口的"文档、校验、执行、展示"被严格分层,而且**模型能看到的和宿主内部的东西严格隔离**。
- **类比**:餐厅。**菜单**(工具 schema)是给顾客(模型)看的;**后厨**(执行逻辑)是餐厅自己的。顾客看不到后厨的燃气表(超时配置、并发标记),后厨也不会把"内部流程"写进菜单。
- **展开**:
  - 每个工具 = `ToolDefinition`:面向模型的 **schema**(名称/描述/参数)+ 宿主内部的 **execute**(执行)、**output**(输出契约)、**timeoutMs**(超时)、**isConcurrencySafe**(能否并行)等。
  - **关键隔离**:注册表通过**显式允许列表**构建给模型看的 schema——`execute`、超时、并发标记这些字段**绝不会泄漏给模型**。
  - **类型安全**:用 `defineTool` 定义工具,一个 schema DSL 同时推导参数和输出类型(精确到 16 层容器,之后退化为 JsonValue)。
  - **执行关卡**:工具调用经过 `pre-execute → execute → post-execute` 三道瀑布式事件,可以在每道关卡插入策略(超时、审批、限流)。
  - **错误处理**:参数错 → `INVALID_ARGS`;输出错 → `INVALID_TOOL_OUTPUT`。宁可显式报错,也不静默降级。
- **30 秒回答**:"工具系统把'模型看到的 schema'和'宿主内部的执行细节'严格隔离,执行经过 pre/post 两道可插拔的关卡。用 defineTool 定义工具可以获得端到端类型安全,并且不支持的 schema 语法会被直接拒绝,保证'要么完整生效,要么明确报错'。"

## 8. 面试题:子代理是什么?怎么管理?

- **一句话**:子代理 = **主 agent 把一部分工作"外包"给另一个 agent**,就像老板把活派给下属;下属还能继续往下派。
- **类比**:公司里老板(主 agent)接了个大项目,拆成几个小任务分给组长(子代理),组长再分给组员。**老板只管结果,不用亲手做每件事**。
- **展开**:
  - 子代理是一个 **seam(可替换能力)**,默认提供方包括:进程内生成、fork 会话、通过 ACP 协议委派、甚至委派给 Codex / Claude Code 等**其他产品**——换一个提供方,系统行为就变了。
  - **能力声明 + fail loud**:每个提供方声明自己支持什么(输出 schema、深度限制、工具过滤、人设)。请求了它不支持的能力,启动前就明确报错——**宁可失败,也不"假装支持然后悄悄缩水"**。
  - **可继续子代理**:普通子代理干完就结束了;可继续的可以"干完再派活"(continue),父 agent 用 `send_message` / `interrupt_agent` / `list_agents` 控制它们。
  - **权限设计**:父 agent 可以过滤子代理能用的工具,但**子代理回报结果用的通道一定保留**——不然它干完活没法交差。
- **30 秒回答**:"子代理是任务委派机制,像公司分层管理:主 agent 把工作分给多个子代理并行处理,子代理还能再往下分。它被设计成可替换的能力(甚至能委派给别的产品),并且坚持 fail loud——能力不匹配就在启动时报错,不让任务悄悄降级。"

## 9. 面试题:安全怎么做?沙箱是什么?

- **一句话**:沙箱 = **给可能危险的操作(执行命令、写文件)套一个"隔离间"**,限制它们能碰什么,防止 AI 一个操作把系统搞坏。
- **类比**:给小孩一个"可以随便玩"的房间——房间里的东西随便碰,但**房间外的(你的电脑、你的银行账户)碰不到**。房间越大,权限越大。
- **展开**:
  - dsh 的沙箱是一个 **seam**(`ctx.sandbox`),有多个平台实现:Linux 用 bwrap/Landlock、macOS 用 Seatbelt、Windows 用 ACL 受限令牌。
  - 三种模式(文件效果层面):
    - `read-only`:只能读,不能写;
    - `workspace-write`:能写工作区目录 + 系统承诺的临时区;
    - `danger-full-access`:不隔离(用户明确授权时)。
  - **诚实报告**:后端会报告自己的强制是 **full**(完整)还是 **partial**(部分,比如旧内核)。要求绝对安全的调用方可以拒绝 partial。
  - 词汇边界:沙箱只管**文件效果**;网络、进程可见性由其他层负责。
- **30 秒回答**:"沙箱是给进程执行套的文件访问策略,有只读、工作区可写、完全放行三档,按平台实现(Linux Landlock、macOS Seatbelt、Windows ACL)。它是个可替换的 seam,并且会诚实报告自己的强制程度是否完整,保证不会'以为被隔离了其实没有'。"

## 10. 面试题:目标、计划、工作流是什么?

- **一句话**:这三个是"**让 agent 干大事**"的机制——目标管"为什么干",计划管"怎么干",工作流管"流水线式地干"。
- **类比**:
  - **目标(Goal)**:长期计划本——"这周把博客上线",记下来,每完成一点就更新状态;
  - **计划(Plan)**:施工图纸——先搭骨架、再装修、最后上线;
  - **工作流(Workflow)**:工厂流水线——一个脚本编排多个子代理,像流水线工人各干一段。
- **展开**:
  - **目标**:有 `active / paused / blocked / complete` 四种持久状态,用"id+版本号"做并发安全的修改(类比:改合同要带版本号,防止两个人同时改)。卡住时记录原因(机器可读的 code + 人读的说明),可以自动续跑直到完成。
  - **工作流**:模型写一个**脚本**(普通 JS,支持顶层 await),脚本里调 `agent()` 启动子代理、`parallel()` 并行、`pipeline()` 流水线。引擎在 **worker 线程**里跑脚本(vm 隔离),`meta`/`args` 是普通 JSON,绝不会把脚本当配置来解析——防止"脚本里的代码被当成配置执行"这类注入。
- **30 秒回答**:"目标、计划、工作流是让 agent 干复杂任务的三件套:目标是持久化、可续跑、带版本号并发控制的长期任务;计划是执行步骤;工作流是模型编写的编排脚本,在 worker 线程沙箱里运行,可以并行启动多个子代理,像流水线一样推进任务。"

## 11. 面试题:它怎么驱动网页界面?

- **一句话**:网页 UI 不是"轮询问状态",而是**订阅会话日志这个事件流**,日志里发生什么,界面就渲染什么。
- **类比**:直播。主播(agent)说的话实时推到观众(UI)屏幕上——不是观众每隔几秒"刷新一下看看有没有新内容",而是**事件一发生就推过来**。
- **展开**:
  - UI 读取活跃 agent(`ctx.agents`)并从 `session/event` 渲染——**UI 本质是会话日志的一个消费者**。
  - 好处:回放(重演历史)和实时看到的内容**天然一致**,因为都来自同一本日志。
  - 客户端插件支持**热更新(HMR)**:开发时改前端插件不用整页刷新。
  - 端口 3080,`npx @deepseek-ai/dsh web` 一键启动,SSH 场景只打印地址。
- **30 秒回答**:"UI 是事件驱动的:它订阅会话事件流并实时渲染,而不是轮询。因为 UI 和回放都消费同一份日志,所以实时与回放永远一致;客户端插件还支持热更新,开发体验很好。"

### 12.2 三个必背金句

1. **"DeepSeek Harness 是开源 agent 框架,核心理念是'一切皆插件',连 agent 循环本身都是可替换的插件。"**
2. **"它的会话日志是唯一真源,坚持'模型可见即已记录',保证可审计、可回放、可恢复。"**
3. **"所有危险能力都走可替换的 seam(工具、文件、沙箱、子代理),并坚持 fail loud——能力不匹配就明确报错,绝不静默降级。"**

### 12.3 常见追问与应对

- **追问"为什么不用现成的框架?"**:答——对比 LangChain 等生态,harness 更强调"宿主可控性 + 可替换性":沙箱、审批、会话审计是它的一等公民,而且没有特权内核,深度定制不用 fork。
- **追问"插件卸载真的能清理干净吗?"**:答——Cordis 的可逆副作用保证注册与撤销成对出现,框架层面保证,不是约定俗成。
- **追问"这么多包,从哪看起?"**:答——先看 `core/agent-loop`(循环怎么转)、`core/tools`(工具怎么执行)、`subagent`(怎么委派),再看 `sandbox` 和 `goal`。文档从 `docs/architecture.zh.md` 开始。

### 12.4 学习路线建议

1. **跑起来**:`npx @deepseek-ai/dsh web`,打开 3080 实际用一次,建立体感;
2. **看架构文档**:[docs/architecture.zh.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md)(本文所有内容都源自它);
3. **拆源码**:从 `packages/core/agent-loop` → `core/tools` → `subagent` → `sandbox` → `goal` 逐个读,对照本文的类比;
4. **动手写一个插件**:加一个自定义工具,体会"挂插件 vs 改内核"的差别——这是理解"一切皆插件"的最好方式。
