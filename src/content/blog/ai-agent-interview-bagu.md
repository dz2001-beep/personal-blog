# AI Agent 面试八股:14 个必考知识点与面试介绍话术

> 本文系统整理 AI Agent(智能体)方向的面试高频考点,覆盖概念、原理、工程与前沿。
> 每个知识点末尾都附一段 **「面试介绍话术」**——按"是什么 → 为什么 → 怎么做 → 价值与边界"的逻辑组织,可以直接流畅地说给面试官听。
> 建议先通读知识点,再重点背诵每段话术的骨架,面试时用自己的话展开。

## 1. 什么是 AI Agent?与普通 LLM 应用的区别

### 1.1 定义

**AI Agent(智能体)** 是一个能够**感知环境、自主决策、调用工具并采取行动**来完成目标任务的人工智能系统。它的核心不是"回答一个问题",而是"**闭环完成一项任务**"。

### 1.2 与普通 LLM 应用的本质区别

| 维度 | 普通 LLM 应用(如聊天机器人) | AI Agent |
| --- | --- | --- |
| 交互模式 | 单轮/多轮问答,一次生成 | 多步循环:规划 → 行动 → 观察 → 再规划 |
| 状态 | 无状态或仅对话历史 | 有目标状态、任务进度、中间结果 |
| 能力边界 | 只能输出文本 | 可调用工具改变外部世界(执行代码、读写文件、调用 API) |
| 终止条件 | 回复完成即结束 | 任务达成(或失败/放弃)才结束 |

### 1.3 面试介绍话术

"Agent 的本质是把大模型从'问答引擎'升级为'任务执行器'。普通 LLM 应用是'你问一句、我答一句',而 Agent 是一个感知-决策-行动的闭环:它先理解目标,规划步骤,调用工具去执行,观察执行结果,再决定下一步,直到任务完成。判断一个系统是不是 Agent,关键看三点:有没有明确目标、能不能自主决策、能不能通过工具作用于外部世界。现在业界讨论的'Agentic'趋势,本质就是把越来越多的应用从被动问答改造成这种主动闭环。"

## 2. Agent 的核心四要素:规划、记忆、工具、行动

### 2.1 四要素模型

学术界和工业界普遍将 Agent 架构抽象为四个核心模块:

1. **规划(Planning)**:把复杂任务分解为子任务,制定执行顺序,并能在失败时调整方案。技术形态包括任务分解、Plan-and-Execute、反思(Reflexion)。
2. **记忆(Memory)**:短期记忆(当前上下文/对话窗口)与长期记忆(向量数据库、知识库、历史经验)。记忆让 Agent 跨轮次保持状态、复用历史经验。
3. **工具(Tools)**:Agent 与外部世界交互的接口,包括代码执行、文件系统、网络搜索、数据库、第三方 API。工具调用通常基于 Function Calling 机制。
4. **行动(Action)**:基于规划与工具结果执行具体动作,并反馈结果形成循环。

### 2.2 四者的关系

四要素不是孤立的,而是构成闭环:**规划决定"做什么"、记忆提供"知道什么"、工具决定"能做什么"、行动产生"做了什么"**,后三者又反哺下一轮规划。

### 2.3 面试介绍话术

"业界公认 Agent 有四个核心模块:规划、记忆、工具、行动。规划负责把大任务拆解成可执行的小步骤,遇到失败还能反思调整;记忆分短期和长期,短期就是当前对话上下文,长期是向量库里的历史知识,让 Agent 能跨会话积累经验;工具是 Agent 触达外部世界的通道,靠函数调用机制让模型决定调哪个接口;行动则把决定真正落地。四个模块循环协作:规划定方向,记忆供知识,工具给能力,行动出结果,结果再反馈给规划。面试官如果追问,我一般强调:这四个模块里,工具和记忆是 Agent 相对普通 LLM 最有区别度的部分。"

## 3. Function Calling:大模型如何调用工具

### 3.1 概念

**Function Calling(函数调用/工具调用)** 是让大模型在生成文本的同时,输出**结构化工具调用指令**(工具名 + 参数 JSON)的机制。模型本身不执行函数,只负责"决定调什么、传什么参数",执行由宿主完成。

### 3.2 完整流程

```text
1. 注册:把每个工具的描述和参数 Schema(JSON Schema)注入提示词/协议
2. 决策:模型在回复中输出 tool_call {name, arguments}
3. 执行:宿主校验参数 → 执行真实函数 → 得到结果
4. 回填:把执行结果作为新的上下文消息还给模型
5. 续推:模型根据结果决定是否继续调用或给出最终答案
```

### 3.3 关键细节

- **Schema 质量决定成功率**:参数描述写得越清楚,模型传参越准。
- **并行调用**:主流模型支持一次输出多个 tool_call,提升效率。
- **错误处理**:工具抛异常时,把错误信息回填给模型,让它自我修正(self-correction)。
- **安全边界**:工具执行必须经过宿主校验与权限控制,模型只负责"建议调用"。

### 3.4 面试介绍话术

"Function Calling 是 Agent 调用工具的标准机制,也是面试几乎必问的点。原理很简单:把每个工具的说明和参数 JSON Schema 注册给模型,模型在回答时不仅能生成文本,还能输出结构化的调用指令,包括工具名和参数。但要注意,模型只负责'决策',不负责'执行'——真正执行的是宿主程序,执行结果再作为消息回填给模型,让它继续推理。我一般会补充三个工程细节:一是 Schema 描述的质量直接影响调用成功率;二是主流模型支持一次并行调用多个工具,能明显提升效率;三是工具执行必须由宿主做权限校验,模型只是建议者不是执行者,这是安全边界的关键。"

## 4. ReAct 范式:推理与行动交替

### 4.1 概念

**ReAct(Reasoning + Acting)** 是一种让模型**交替进行"推理(Reason)"与"行动(Act)"**的 Agent 范式:模型先思考当前状态与下一步,再调用工具或采取行动,观察结果后继续思考,形成"思考→行动→观察"的循环。

### 4.2 机制

```text
Thought(推理):基于当前信息判断下一步
Action(行动):调用工具或给出动作
Observation(观察):获得工具执行结果
→ 回到 Thought,循环直到任务完成
```

相比纯 Chain-of-Thought(链式思考),ReAct 让推理**接地于外部事实**(工具返回的真实结果),减少凭空推理的幻觉;相比纯行动,ReAct 保留推理链,可解释、可调试。

### 4.3 面试介绍话术

"ReAct 是 Agent 最经典的执行范式,核心是'推理和行动交替进行'。每一步模型先 Thought 一下,判断现在该干什么,然后 Action 调用工具,再根据 Observation 的真实结果继续推理,形成循环。它解决了两个问题:一是让推理有事实依据,不靠模型瞎猜,减少幻觉;二是让整个决策过程有迹可循,可解释、可调试。现在很多 Agent 框架的循环引擎本质上都是 ReAct 的工程化实现,区别主要在记忆管理、并行化和失败恢复这些工程细节上。"

## 5. 规划与任务分解:Plan-and-Execute 与反思

### 5.1 概念

**规划(Planning)** 指 Agent 在行动前先制定整体方案:把复杂目标分解为有序子任务,并为每个子任务选择策略。典型范式:

- **Plan-and-Execute**:先规划(Plan)后执行(Execute),先产出一份任务清单,再逐项执行,避免边做边想导致的失控。
- **任务分解(Task Decomposition)**:把大任务拆成小任务,如 Chain-of-Thought、Tree of Thoughts(树状思维)、子代理分工。
- **反思(Reflexion)**:在任务失败或结果不理想时,让模型回顾失败原因,总结经验并调整策略,形成"执行-反思-改进"循环。

### 5.2 关键点

- 规划粒度要匹配模型的上下文与能力边界;过度细化成本高,过度粗放容易遗漏。
- 规划结果应可校验、可回退;执行失败时应触发重新规划而非死循环。
- 反思是提升长任务成功率的关键:多数 Agent 的长任务失败来自"错了不回头"。

### 5.3 面试介绍话术

"关于规划能力,我会分三个层次讲。第一是 Plan-and-Execute,先制定完整任务清单再执行,适合目标明确的任务,避免边做边失控;第二是任务分解,把复杂目标拆成可执行的小步骤,也可以分给子代理并行处理;第三是反思,这是最容易被忽视但最关键的——Agent 在长任务里最常见的失败就是错了不回头,而 Reflexion 机制让模型在执行后回顾失败原因、调整策略,形成'执行-反思-改进'的闭环。面试时我还会强调:规划不是一次性产出,而是要支持动态调整,因为真实环境里任务执行经常会遇到计划外的结果。"

## 6. 记忆系统:短期记忆与长期记忆

### 6.1 概念

Agent 的**记忆**是其在多轮任务中保持状态与知识的能力,分两类:

- **短期记忆(Short-term)**:当前任务的上下文,受模型上下文窗口限制,通常用对话历史 + 摘要/压缩管理。
- **长期记忆(Long-term)**:跨会话持久化的知识,通常用**向量数据库**存储,通过**语义检索**(RAG)按需召回;也包括结构化数据库、文件等外部存储。

### 6.2 机制

- **上下文管理**:窗口溢出时采用滑动窗口、摘要压缩(compaction)、关键信息提取。
- **记忆写入与召回**:重要信息写入长期记忆(带时间戳、来源),任务开始时按相关性检索召回。
- **记忆演化**:经验/教训沉淀,让 Agent 越用越"熟"。

### 6.3 面试介绍话术

"记忆系统解决的是 Agent'怎么记住东西'的问题,我习惯分短期和长期两层讲。短期记忆就是当前任务上下文,受模型窗口限制,所以要做上下文管理,比如滑动窗口、摘要压缩;长期记忆是跨会话的持久知识,典型做法是向量数据库加语义检索——把重要信息向量化存起来,任务开始时按相关性召回。我还会提一个工程细节:记忆一定要带来源和时间戳,检索回来才知道可信度,否则长期记忆反而会引入错误信息。面试官如果追问'长任务上下文爆炸怎么办',答案就是分层记忆加压缩,这也是很多框架里 compaction 模块存在的意义。"

## 7. Agent 与 RAG:区别与结合(Agentic RAG)

### 7.1 概念

**RAG(Retrieval-Augmented Generation,检索增强生成)**:先从知识库检索相关文档,再让模型基于检索结果生成,解决"知识过时、幻觉、私有知识"问题。

### 7.2 区别

| 维度 | RAG | Agent |
| --- | --- | --- |
| 目的 | 增强"回答"的知识准确性 | 完成"任务"的自主闭环 |
| 流程 | 固定:检索 → 生成 | 动态:规划 → 工具 → 观察 → 循环 |
| 工具 | 检索器(向量库) | 任意工具(代码/API/搜索/数据库) |

### 7.3 结合:Agentic RAG

现代架构中二者融合:**Agent 把"检索"也当成一个工具**,可以自主决定何时检索、检索几次、检索哪些库、是否需要追问用户——比固定流水线的 RAG 更灵活,被称为 Agentic RAG。

### 7.4 面试介绍话术

"RAG 和 Agent 是面试常被对比的两个概念。我的理解是:RAG 解决'知识从哪来',Agent 解决'任务怎么做'。RAG 是固定的检索-生成流水线,适合问答类场景;Agent 是动态的决策循环,适合多步骤任务。现在两者正在融合,叫 Agentic RAG——Agent 把检索当成一个普通工具,自主决定什么时候查、查几次、查完还要不要调别的工具。面试时我会说:不要把它们对立,真实产品里往往是 Agent 的外壳、RAG 的内核,一个处理任务编排,一个处理知识供给。"

## 8. 多智能体系统(Multi-Agent)

### 8.1 概念

**多智能体系统**:多个 Agent 以不同角色协作完成复杂任务,常见模式:

- **角色分工**:规划者、执行者、审查者(如 MetaGPT 的 PM/架构师/工程师角色)。
- **协作模式**:顺序流水线(一个的输出是下一个的输入)、并行分工、辩论/审查(一个产出、一个挑错)。
- **通信方式**:消息传递、共享黑板(blackboard)、共享任务队列。

### 8.2 价值与代价

- 价值:并行加速、角色隔离(让审查者独立于执行者)、复杂任务建模更自然。
- 代价:通信开销、上下文传递损耗、协调复杂度、成本翻倍——**多 Agent 不是银弹**,单 Agent 配好工具在多数场景更划算。

### 8.3 面试介绍话术

"多智能体系统我会讲三点:模式、价值和代价。模式上主要是角色分工加协作,比如规划者拆任务、执行者干活、审查者挑错,通信靠消息传递或共享状态;价值在于能并行、能角色隔离,审查者独立于执行者能提高质量;但代价也很明显——通信开销、上下文损耗、成本成倍增加。所以我的观点是:面试官如果问'要不要上多 Agent',标准答案不是'越多越好',而是'单 Agent 加工具能解决就别上多 Agent',多 Agent 适合任务天然可分、需要角色隔离的场景。"

## 9. Agent 的安全与可靠性

### 9.1 风险面

- **提示注入(Prompt Injection)**:外部输入(网页、文档)夹带恶意指令,劫持 Agent 行为。
- **工具滥用**:Agent 调用高风险工具(删除文件、转账、发邮件)造成破坏。
- **幻觉与累积误差**:单步小错在多步循环中放大。
- **失控循环**:Agent 在错误状态下反复重试,消耗资源。

### 9.2 工程对策

- **沙箱隔离**:代码执行放入沙箱(权限受限、资源受限),如文件级读写策略、进程隔离。
- **审批机制**:高危工具调用需人工确认(approval)。
- **权限最小化**:Agent 只拥有完成任务所需的最小工具集与权限(工具过滤、deny 列表)。
- **输入消毒与指令边界**:对不可信输入做隔离,明确"外部内容不是指令"。
- **失败恢复与熔断**:超时、重试上限、最大轮次限制、人工介入通道。

### 9.3 面试介绍话术

"Agent 安全这块面试官很爱深挖,我会从风险和对策两面讲。风险主要有四个:提示注入,外部内容伪装成指令劫持 Agent;工具滥用,模型被诱导调用危险工具;幻觉在多步循环里累积放大;还有失控死循环。对策上:代码执行必须进沙箱,给文件读写做策略限制;高危操作走人工审批;权限最小化,Agent 只有完成任务的最小工具集;对不可信输入做边界隔离。最后一定要有熔断机制——最大轮次、超时、重试上限,让系统'可以犯错但不能无限犯错'。安全设计的原则是纵深防御,每一层都假设上层会失守。"

## 10. Agent 的评估

### 10.1 难点

Agent 评估比普通 LLM 评估难:结果路径多样(同一任务不同解法)、过程与结果都要看、成本高(需要真实工具环境)。

### 10.2 评估维度

- **结果评估**:最终任务是否达成(成功率)、产出质量(人工/LLM-as-Judge 打分)。
- **过程评估(Trajectory Evaluation)**:规划是否合理、工具调用是否高效、是否浪费轮次。
- **鲁棒性**:对输入扰动、工具故障、歧义目标的适应能力。
- **成本指标**:token 消耗、调用次数、延迟。

### 10.3 评估方法

- 任务集 + 黄金答案(Gold Answer)对比。
- LLM-as-Judge 自动打分 + 人工抽检结合。
- 沙盒环境评测(如 AgentBench、SWE-bench 类基准)。

### 10.4 面试介绍话术

"Agent 评估我会强调'比 LLM 评估难在哪'和'怎么评'两部分。难在三点:一是解路径多样,同一个任务不同 Agent 解法完全不同,没法简单比对;二是过程和结果都得看,结果对了但绕了十圈也算差;三是评估要真实工具环境,成本高。所以评估维度要分结果和过程:结果看任务成功率、产出质量,过程看规划合理性和轮次效率,再加上成本指标。方法上任务集加黄金答案对比,LLM 当裁判自动打分,配合人工抽检,有条件就上 AgentBench 这类沙盒基准。面试时能说出'结果+过程+成本'三维度,基本就能体现你真的落地过。"

## 11. 主流 Agent 框架对比

### 11.1 框架速览

| 框架 | 定位 | 特点 |
| --- | --- | --- |
| LangChain / LangGraph | 通用 LLM 应用框架 | 生态最大;LangGraph 引入图状状态机,适合可控流程 |
| AutoGen / AG2 | 多智能体框架 | 强调多 Agent 对话协作 |
| CrewAI | 多智能体框架 | 角色化编排,上手快 |
| MetaGPT | 多智能体框架 | 软件公司角色模拟,面向软件开发 |
| DeepSeek Harness(dsh) | 开源 Agent Harness | "一切皆插件",事件溯源会话日志、可替换能力 seam、沙箱一等公民 |
| OpenAI Swarm / Agents SDK | 轻量多 Agent | 官方风格,简单直接 |

### 11.2 选型视角

- 单 Agent + 工具:轻量框架或直接 harness 类平台。
- 多 Agent 协作:AutoGen/CrewAI/MetaGPT 类。
- 生产级可控:需要状态机、可观测性、沙箱,倾向 LangGraph 或 Harness 类。
- 面试加分:能对比"框架 vs 自研""为什么选它",而不是只会列名字。

### 11.3 面试介绍话术

"框架对比这种题,我会先给分类再给选型逻辑,而不是背名字。按定位分三类:通用编排类,像 LangChain、LangGraph,生态最大,图状状态机适合生产级可控流程;多智能体类,像 AutoGen、CrewAI、MetaGPT,侧重角色分工协作;还有 Harness 类,比如 DeepSeek Harness,把工具、沙箱、会话、审批这些基建全部插件化,强调宿主可控性和可替换性。选型逻辑是:任务简单就单 Agent 加工具,别上重框架;需要可控流程选图状状态机;需要多角色协作选多 Agent 框架;对安全、可观测性要求高的生产场景,我会倾向 Harness 类或者自研核心循环。我自己的观点是框架只是起点,真正要解决的是状态管理、可观测性和失败恢复这三个工程问题。"

## 12. Agent 的工程落地

### 12.1 核心工程问题

- **状态管理**:Agent 是多步有状态系统,状态(任务进度、中间结果、上下文)必须可持久化、可恢复、可回放。
- **可观测性**:完整记录每一步的输入输出(事件日志),支持追溯、回放、调试——这是生产 Agent 的命脉。
- **容错与恢复**:超时、重试、幂等、断点续跑、人工接管。
- **成本控制**:token 预算、调用次数上限、缓存、模型分级(简单步骤用小模型)。
- **并发与资源**:多任务并发、限流、队列。

### 12.2 关键原则

事件日志即唯一真源 → 一切视图(UI/回放/审计)从日志派生;失败可重放,成功可追溯。

### 12.3 面试介绍话术

"聊 Agent 工程落地,我会强调四个问题,这也是面试官判断你有没有生产经验的地方。第一是状态管理,Agent 是多步有状态系统,状态必须能持久化、能恢复,不能任务干到一半重启就全丢;第二是可观测性,我坚持事件日志是唯一真源——把每一步的输入输出都记下来,UI、回放、审计全从日志派生,出问题能回放定位,这是生产环境的命脉;第三是容错,超时、重试、幂等、断点续跑、人工接管一个都不能少;第四是成本,要控 token 预算、限制调用次数、按难度分级用模型。一句话总结:写 Demo 只要循环,上生产要的是状态、日志和熔断。"

## 13. Agent 的局限与挑战

### 13.1 核心挑战

- **幻觉与错误累积**:单步小错在多步循环中被放大,长任务成功率随步数指数下降。
- **上下文与记忆瓶颈**:窗口有限,长任务中早期信息丢失或占位。
- **成本与延迟**:多步循环的 token 消耗与推理延迟远高于单次问答。
- **工具生态不完善**:真实世界接口脏乱差,工具质量决定 Agent 上限。
- **评估困难**:多样性解路径使自动化评估难以对齐。
- **安全与信任**:自主执行带来不可控风险,阻碍高价值场景落地。

### 13.2 面试介绍话术

"关于 Agent 的局限,我最想讲的是'错误累积'——这是 Agent 和单次 LLM 调用最本质的差异:单次回答错了就错了,Agent 错了会带着错误继续往下走,步数越多误差越大,所以长任务成功率天然会掉。其次是上下文瓶颈,窗口有限,任务一长早期的关键信息就丢了,要靠分层记忆和压缩来缓解。然后是成本和延迟,多步循环意味着成倍的 token 和推理时间。最后是安全信任问题,自主执行带来不可控风险,这恰恰是它还没有大规模落地的核心原因。我的判断是:Agent 的能力上限在模型,落地上限在工程——幻觉、成本、安全这些都可以靠工程缓解,但不可能靠工程根除。"

## 14. 总纲:如何向面试官系统介绍 Agent

> 适用场景:面试官让你"聊聊你对 Agent 的理解"——按下面这个三段式,3 分钟讲完,逻辑闭环。

**第一段(定位)**:"Agent 是把大模型从问答引擎升级为任务执行器的系统,核心是感知-决策-行动的闭环,四大模块是规划、记忆、工具、行动。"

**第二段(机制)**:"执行层面,主流范式是 ReAct,推理与行动交替;工具靠 Function Calling 让模型输出结构化调用指令,宿主执行后回填结果;长任务靠规划分解、分层记忆和反思纠错;复杂场景可以用多 Agent 角色分工,但要注意协调成本。"

**第三段(工程与判断)**:"真正上生产,要解决状态管理、可观测性、容错熔断和成本控制四个问题;同时要正视局限——错误累积、上下文瓶颈、成本和安全,这些决定了 Agent 的落地节奏。我的总体判断是:模型决定 Agent 的能力上限,工程决定它的落地上限。"
